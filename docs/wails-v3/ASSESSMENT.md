## Assumptions / test environment

Rules for every later milestone that runs anything:

1. **Never launch Mailven against the owner's data.** Real data lives under `$XDG_CONFIG_HOME/mailven`, `$XDG_DATA_HOME/mailven` and `$XDG_CACHE_HOME/mailven` (`internal/platform/paths.go`, `getLinuxPaths`), falling back to `~/.config`, `~/.local/share`, `~/.cache`. Runtime sockets use `$XDG_RUNTIME_DIR/mailven` (`internal/platform/socketdir_unix.go`).
2. **Isolated profile.** Run with a throwaway `HOME` and all four `XDG_*` variables (`CONFIG`, `DATA`, `CACHE`, `RUNTIME`) pointing into one empty temp directory outside the repo.
3. **Isolated keyring.** Credentials use the Secret Service through `go-keyring`. Run under `dbus-run-session` with a private, unlocked test keyring (or none, so credential calls fail visibly) so no real secret is read or written. Exact setup is unrun and is a prerequisite to define in M5.
4. **Synthetic mail only.** No real accounts. Use the backend-free UI harness (`make test-ui`: Vite plus fake bindings; every non-read binding rejects with `blocked: <name>`) for frontend checks, and a local test IMAP/SMTP server with generated fixtures for backend or native checks. The server and fixtures do not exist yet; designing them is M5.
5. **Display.** Native launches need a display; `Xvfb` is missing here. A spike should use a nested Wayland compositor or install Xvfb only with owner approval (no package installs without approval).
6. **Disposable worktree for any prototype.** Per the brief, a spike is separately approvable, runs in a throwaway worktree on its own branch, and never commits to `main`.
7. **Version pinning.** Use an exact Wails v3 tag in any experiment (no `@latest`); record the tag and date.

Open questions for later milestones (research risks, not findings): whether `dbus-run-session` plus a headless keyring reproduces the Secret Service behavior the app expects; which display strategy works for GTK4/WebKitGTK 6.0 on this host; whether MA13 should land before a spike.

### Security advisories (official, [advisory list](https://github.com/wailsapp/wails/security/advisories))

- v3 advisories published 2026-10-18 (server-mode CSRF/WebSocket origin, Windows notification PowerShell injection, macOS child frames, `wails3 init -t`) are all patched at or before `3.0.0-beta.31`; none is open against v3.1.0. Mailven's relevant surface is desktop, not server mode.
- [GHSA-r5j2-ghh9-2jqw](https://github.com/wailsapp/wails/security-advisories/GHSA-r5j2-ghh9-2jqw) (v2, Linux iframe bridge, high; fixed v2.17.1) is the same WebKitGTK limitation v3 documents. **Mailven-relevant:** `frontend/src/lib/components/viewer/EmailBody.svelte:404-407` renders untrusted mail in an `<iframe sandbox="allow-scripts allow-popups allow-popups-to-escape-sandbox">` (no `allow-same-origin`, opaque origin). v3.0.0 notes say sandboxed frames without `allow-same-origin` are blocked from the native message handler on Linux, but **"bound-method calls from child frames go over HTTP to `/wails/runtime`, so the guard does not restrict them; treat any iframe as having access to your bound Go methods."** Whether a script-enabled sandboxed mail frame can reach `/wails/runtime` (and so bound methods) in v3 is **unknown and security-critical**; it must be answered in M2/M3 from tag source (`messageprocessor*`, `assetserver`) and, if still open, by a gated spike. Do not migrate until resolved. The same exposure question applies to v2.16.0 today; see MA13.

### Engine improvements vs API/framework improvements

- **API/ABI name vs engine version.** `webkitgtk-6.0` and `webkit2gtk-4.1` are API series (GTK4 vs GTK3 widget toolkit); the browser engine version is the WebKitGTK `2.x` release (stable `2.54.3`, 2026-11-18, [webkitgtk.org](https://webkitgtk.org/)). webkitgtk.org's stable reference documents "WebKit2 – 4.1" (`webkit2gtk-4.1`), i.e. 4.1 is still current API, not frozen.
- **Engine-level changes shipped in 2.54.0** ([release note, 2026-09-16](https://webkitgtk.org/2026/09/16/webkitgtk2.54.0-released.html)): Skia replaces TextureMapper in the web-process compositor, improved damage handling, GPU atlas for image uploads, cairo 2D option removed, new favicon API, `magnification` property, per-navigation User-Agent. The note does **not** limit any of these to the 6.0 API; they are web-process/engine features and the same 2.54 build provides the 4.1 API (host evidence above). So CSS/JS, compositor, GPU and sandbox gains reach 4.1 builds that ship the same engine version.
- **Not verified:** whether any WebKitGTK feature is exclusive to the 6.0 API (for example GTK4 scene-graph integration or API additions); the 2.54 note lists none, but the tarball `NEWS` was not read. Any GTK4 rendering, scrolling or startup-time benefit for Mailven is **an unverified hypothesis**; no performance promise is made. Distros pin their own engine versions, so the gain depends on the user's distro, not on Wails.
- **Framework/API benefits (v3-only, independent of GTK4):** service-based bindings and a Go-side generator, typed events, multi-window API, first-party notification and single-instance services, `Hidden` window option, `RegisterHook` window events. These need the Wails upgrade, not GTK4.
- **GTK4-specific benefits:** portal-based file dialogs by default, GNOME HIG menu style, GTK4 toolchain currency. Mailven already works around portals for Flatpak (`app/attachment.go`), so benefit is unquantified.

### v3 readiness assessment

**Verdict: v3.1.0 is a stable, supported desktop release and GTK4/WebKitGTK 6.0 is its default Linux path, but readiness for Mailven is conditional — not yet decision-ready for GO.** Proceed to inventory (W3-M2) and design (W3-M3); do not plan implementation until blockers are cleared.

Potential blockers/risks for Mailven (research risks, not verified defects):

1. **Untrusted email iframe and `/wails/runtime`** (above): security-critical unknown.
2. **No GTK3 safety net**: `-tags gtk3` still exists but is announced for removal; Mailven would target GTK4/WebKitGTK 6.0, which Debian 12 / Ubuntu 22.04 lack (Flathub GNOME 50/51 SDKs ship `webkitgtk-6.0`, per the brief).
3. **Spellcheck** has no v3 API; Mailven's compose/spellcheck behavior must be mapped in M2 (WebKit default spellchecking via the engine versus Mailven dictionaries is unverified).
4. **Detached composer** relies on two Wails apps and IPC; v3 multi-window changes the model (M3), and `window.open`/custom protocol gaps are open.
5. **Release velocity/maintenance**: heavy automated (`@taliesin-ai`) contribution volume in v3.1.0 notes and an unexplained 16-day release gap since 2026-11-03; v3.1.0 is the first release after GA. Judgment, not a finding; re-check before any spike.
6. **Docs vs source drift** (GTK3 removal statement) shows documentation cannot be trusted over the tag; each M2 mapping must cite tag source.

Unrun checks: building anything with `wails3`/`-tags gtk3`, `wails3 doctor`, running the CLI, any GUI or Wayland run, reading `NEWS` inside the WebKitGTK tarball, Windows/macOS-specific source review, and reading Wails issues beyond the label searches above. All remain for M2–M5 or a gated spike.

## Architecture options and decision

Recorded by [W3-M3](../../PLAN.md#w3-m3) on 2026-11-19 on branch `docs/wails-v3-assessment` from `6b3febc`. Design only: no prototype, build or generator run. Mailven claims are **checked** (`path:line` or symbol in this checkout); v3 claims are **read** from tag `v3.1.0` of `wailsapp/wails` (`gh api repos/wailsapp/wails/contents/v3/<path>?ref=v3.1.0`). Extension work was checked against [EXT_RULES](../EXT_RULES.md) R1–R6, R25–R33.

### Facts that shape the design

1. **Composer logic is already shared.** `composeOps` and `draftOps` are built by both `App.Startup` (`app/app.go:553`; `composeOps` at `:771`) and `ComposerApp.Startup` (`app/detached_composer.go:124-262`). The composer process re-creates about twenty stores plus its own DB handle, credential store, S/MIME/PGP stack and a one-connection IMAP pool. Per-window state is small: `currentDraft`, `draftSyncCancel/Done`, `config` (account, mode, draft, mailto).
2. **Send semantics differ today.** `App.SendMessage` queues through the undo-delay `sendQueue` (`app/compose.go:692-728`, flushed by `finishBeforeQuit`, `app/send_queue.go:185`). `ComposerApp.SendMessage` sends at once (`detached_composer.go:666`), persists a recovery draft first, then reports to main over IPC (`message_sent` → `syncSentFolder`, `app/ipc.go:104`). Option B must not silently unify these.
3. **Lifetimes are independent today.** A composer is a separate process (`OpenComposerWindow`, `app/ipc.go:196`, token over stdin); quitting main does not close open composers, and a composer crash cannot take down mail sync. `shuttingDown` is a process-global in `app/app.go`.
4. **Bound-call window identity is client-asserted.** v3 reads `x-wails-window-id`/`-name` from request headers (`transport_http.go:325-336`) and puts the resolved window in the call context (`messageprocessor_call.go:134-136`, `WindowKey`). It routes; it does not authenticate. On desktop `checkRuntimeRequest` always returns true (`transport_http_notserver.go:10`), and the Linux child-frame guard covers only the native message handler (`linux_child_frame_guard.go` header comment).
5. **Closing a window cancels its pending bound calls** (`CancelWindowCalls`, `webview_window.go:1188-1190`; calls run under a context derived from the request). A send or draft sync run under that context would abort on window close.
6. **One `application.New` per process.** v3 keeps a single `globalApplication`; the composer-per-process model therefore needs no v3 feature, and in-process composers need `app.Window.NewWithOptions`.
7. **Native context menu can be disabled**: `WebviewWindowOptions.DefaultContextMenuDisabled` exists (`webview_window_options.go:225`), which closes inventory question 6 for the custom spell menu. Window-targeted events exist (`WebviewWindow.EmitEvent`, `webview_window.go:260`) next to app-wide `app.Event.Emit`; the close veto is `RegisterHook(events.Common.WindowClosing, …)` with `WindowEvent.Cancel` (`:1007`, `:162`).
8. **Correction to the W3-M2 inventory:** 46 extension frontend files import `$wailsjs` (36 `models`, 29 `App`, 4 `runtime`; about 17 `EventsOn` references), not 16. Extension **Go** code imports no Wails package; its events reach the frontend through `coreapi` → `app/eventbus.go`, so event emission changes in the host only.

### Options

| | **A. Compatibility-first** (keep composer process + IPC) | **B. One v3 application, native composer windows** |
|---|---|---|
| Shape | Two `application.New` runs as today (`main.go:159`, `:253`), same `--compose` re-exec and `internal/ipc` | One process, `app.Window.NewWithOptions{URL:"/composer.html"}` per composer; `internal/ipc` and `composerAssetHandler` removed |
| Window-specific state | Process-global as today | Needs a per-window composer controller keyed by window ID from the call context; `ComposerApp` singleton can no longer hold `currentDraft` |
| Shared services | Duplicated per process (DB handle, credentials, IMAP pool); cross-process SQLite writers already work (WAL, `busy_timeout(30000)`, `internal/database/database.go:60`) | One pool, one DB handle, one `sendQueue`; removes the second keyring/DB init and one cgo/WebKit start per composer |
| Failure isolation | Composer crash or hang cannot affect sync; a composer outlives main | Any panic outside a `recoverPanic` goroutine ends every window; closing main must decide what happens to open composers |
| Send / draft safety | Unchanged code and semantics | New concurrency surface: two windows on one draft, send ctx cancelled by window close (fact 5), undo-queue vs immediate send, `shuttingDown` global |
| v3 risk | Smallest; `window.open`/custom-protocol issues ([#5043](https://github.com/wailsapp/wails/issues/5043), [#4026](https://github.com/wailsapp/wails/issues/4026)) do not apply | Depends on multi-window behaviour on GTK4 (focus, hidden start, per-window GPU/preinit) which is unverified |
| Prerequisites | Bindings and events port (shared by both); preinit/`webkit_preinit_linux.go` decision | Everything in A, plus quit semantics, per-window controller, draft-ownership lock, race tests |
| Rollback | Revert is the v2 branch; composer path identical to today | Same, plus a design reversal if multi-window proves flaky; A is the fallback inside the same v3 branch |
| Benefit | Lowest blast radius; no behaviour change a user can see | Fewer processes, faster composer open, one source of truth for sends, removes about 1,500 lines of IPC glue (`internal/ipc` about 1,200, `app/ipc.go` 303) and the composer re-initialisation |

**Staged A → B is viable** because the frontend already hides the choice behind `ComposerApi` (`frontend/src/lib/composerApi.ts`, 5 consuming files), and `composeOps`/`draftOps` are already process-agnostic. Removing IPC is not automatically safer: it deletes an isolation boundary (fact 3) and moves today's cross-process coordination into in-process locks that do not exist yet.

### Recommendation

1. **Migrate Option A first**; treat B as a separate, later decision gated on a spike. This answers "what first": bindings and events port, lifecycle, window shape, build, with the composer left as a process.
2. **Defer B** until A ships and these are shown by a synthetic-data spike: per-window controller with a draft-ownership lock, a quit rule for open composers, send context decoupled from the call context, and clean multi-window behaviour on GTK4/Wayland.
3. **Independent of the migration** (can be done on v2 now): add an explicit `connect-src 'none'` to the mail iframe CSP (see Security); both are recorded in [MA13](../../ISSUES.md#ma13).

### Cross-window state, events and races (Option B requirements; A keeps today's process isolation)

- **Events:** use `WebviewWindow.EmitEvent` for composer-scoped events (draft sync status, `composer:*`) and `app.Event.Emit` only for application-wide events; composer subscribes to a short allow-list. All windows are equally trusted, so broadcast is a hygiene concern, not a boundary.
- **Per-window controller:** `map[windowID]*composerSession` holding `currentDraft`, sync cancel/done and config, created on window open, removed on close; resolved from `ctx.Value(application.WindowKey)`. Because window IDs are client-asserted (fact 4), every method must also validate `draftID`/`accountID` ownership server side and must not treat the window ID as authority.
- **Duplicate sends and corrupt drafts:** one in-process mutex or ownership record per draft ID (second window opening the same draft focuses the first or refuses); keep `persistRecoveryDraft` before transport and the `submission` attempt record as the single source of truth for "sent". Run send and IMAP draft sync under an application-lifetime context, never the bound-call context (fact 5); on composer close, either finish or cancel explicitly and keep the recovery draft.
- **Quit rule:** quitting main with open composers must prompt or flush each composer's draft before exit; today that case does not exist (fact 3).
- **Race tests to write at implementation time (not run):** double Send click and Send from two windows on one draft; close during send; close during draft sync; `SaveDraft` after `DeleteDraft`; two composers on different accounts with one IMAP pool; quit during undo-delay.

### Security boundary analysis

- **Email HTML:** sanitized by `internal/email/sanitizer.go`, rendered in `<iframe sandbox="allow-scripts allow-popups allow-popups-to-escape-sandbox" srcdoc>` (`EmailBody.svelte:403-408`) with a meta CSP `default-src 'self' data:; img-src …; style-src 'unsafe-inline'; script-src 'unsafe-inline'` (`emailBodyIframe.ts:200`). No `allow-same-origin`, so the frame has an opaque origin and cannot read `window.parent` or the native handler.
- **HTTP bridge is the open path.** From source: v3 desktop applies no origin or frame check to `/wails/runtime` (fact 4), and window ID headers are client-controlled. So the question "can sandboxed script call a bound method" reduces to whether the frame can issue `fetch('/wails/runtime', {method:'POST'})` at all. Three independent barriers are plausible but **none is verified**: the opaque-origin cross-origin request (CORS preflight on a JSON POST handled by the custom scheme handler), the CSP `default-src 'self'` (`connect-src` falls back to it, and whether `'self'` matches an opaque-origin `srcdoc` document in WebKitGTK is unverified), and sanitizer script stripping. Treat the question as **open**; the gate is the synthetic-HTML spike already specified in the inventory.
- **Cheap hardening, independent of the migration:** add `connect-src 'none'` (and `form-action 'none'`, `frame-src 'none'`) to the iframe CSP so network and bridge access no longer depend on the `'self'` interpretation. Not changed here (design milestone); noted on MA13.
- **Privileged methods:** with all 428 + 41 methods reachable by any caller that reaches the bridge, the highest-value targets are file-reading and sending methods: `ReadFileAsAttachment` (`detached_composer.go:892`), attachment save/open paths (`app/attachment.go`), `SendMessage`, credential-adjacent settings. Existing path validation and token-gated IPC stay; Option B adds no new privileged surface but removes the IPC token boundary between composer and main.
- **Navigation:** `BrowserOpenURL` sites (5 Go, 6 frontend) keep scheme allow-listing as today; v3 `app.Browser.OpenURL` has no policy of its own (read `browser_manager.go` at spike time).

### Performance measurements

## Executive decision

**Status: proposed by [W3-M7](../../PLAN.md#w3-m7) on 2026-11-19; not owner-approved.** This section recommends a decision and asks for none of the work below to start without separate owner authorization. Inputs: the sections above (W3-M0 to W3-M5), [MIGRATION_BLUEPRINT.md](MIGRATION_BLUEPRINT.md) (W3-M6), an independent read-only review (below), and a release re-check on 2026-11-19 (`gh api repos/wailsapp/wails/releases`: v3.1.0 is still the latest stable; newest nightly `v3.2.0-nightly.20261103`).

### Recommendation: DEFER the migration (proposed)

Do not authorize any v3 implementation stage (S2 onward) now. Do the v2-side work that the assessment shows is useful whatever the decision, and answer the two blocking unknowns with separately approved spikes. Re-run this decision when the [conditions](#conditions-for-a-conditional-go) hold; the expected next outcome is a conditional GO for stages S2 to S5.

### Conditions for a conditional GO

1. [MA13](../../ISSUES.md#ma13) is resolved (v2.17.1 or later on `main`), so the v2 baseline is fixed.
2. Stage S0 is done: fixtures FX-1, FX-3, FX-5 and FX-6 exist, G0 isolation is proven on v2, PERF-1 to PERF-7 baselines are recorded, and the `connect-src 'none'` CSP hardening has its SEC-3/SEC-4 result on v2.
3. SP-1 finds no iframe-to-bridge path on v3.1.0 (or a tested mitigation), SP-3 builds and launches a minimal GTK4 app in an Ubuntu 24.04+/Debian 13+ container and the GNOME 50 SDK, and SP-2 shows zero missing bound methods.
4. The pin is re-checked: v3.1.0 or a newer stable release with no open Linux regression affecting the matrix.

### Critical blockers (ranked)

1. **Email iframe to `/wails/runtime`** (G4, SP-1): security; also relevant on v2 through GHSA-r5j2-ghh9-2jqw ([MA13](../../ISSUES.md#ma13)).
2. **GTK4 toolchain:** runners, Flatpak SDK build and `webkit_preinit` relink unproven (SP-3, SP-6, PKG-1).
3. **No test infrastructure for the real app:** FX-1 to FX-6 and a display wrapper must be built before any gate can run.
4. **Windows and macOS:** only verifiable with owner hardware (PKG-6, PKG-7).
